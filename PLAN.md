## Stage 0 fidelity investigation — verified findings (2026-10-22, Hermes; supersedes chat-thread conclusions)
All verified against artifacts (xcresult bundles in DerivedData `Observatory-cbfacmzpikqjyicwfyxiegxppwiy/Logs/Test/`, ffmpeg volumedetect, source code):
- **On-device vs server diagnostic** (physical iPhone 16 Pro / iOS 27.0.1, run 2026-10-21 20:29, `Test-Observatory-2026.10.21_20-29-24--0700.xcresult`): on-device = 3 words (fixture-multi-a) / 1 word (fixture-multi-b); server = 261 / 182 words with 2 speakers found in both. The weakness is specific to the on-device path — same files, same harness, same device, only `requiresOnDeviceRecognition` flipped.
- **Chunked replay (≤55s, matching production's ~1-min rollover) improves on-device counts 9–29×** (multi-a 27/288, solo 28/149, multi-b 29/192 = 9–19% fidelity), but tail-truncation persists *within* chunks (multi-a's first 0–55s chunk yields words only from offset 49.9s). Request lifecycle is a real contributing factor, not the whole story.
- **NOT overlap-specific — earlier framing retracted.** fixture-solo (single speaker, no overlap) also fails at 19% fidelity on-device.
- **Prime suspect: capture gain / disabled DSP.** Production records with `AVAudioSession .record + .measurement` (`SpeechRecognitionManager.swift` ~line 589, chosen in commit `3c46d9b`). `.measurement` disables system AGC/processing → raw low-level signal. Measured fixture levels (ffmpeg volumedetect): mean −37.4 dB (multi-a), −38.1 dB (multi-b), **−46.5 dB (solo)**; peaks −13.5 to −20.2 dBFS. Quiet/distant audio is the documented failure mode of the on-device recognizer (near-empty final results, no error). Note: Siri's far-field robustness (heard car radio via AirPods) comes from its private front-end (multi-mic beamforming, AGC, AEC, Siri Understanding assets), NOT a better public recognizer — not a valid comparison, but it proves device-side conditioning is the lever.
- **Fixture provenance caveat:** fixtures recorded 2026-10-15 ~13:55, roughly an hour *before* the `.measurement` tuning was committed (14:52) — confirm whether they represent the current capture config.

### Experiment queue for the fidelity investigation (run in this order; device runs need user approval per CONVENTIONS.md)
1. **E4 — device asset check: DONE (2026-10-22), clear.** Dictation enabled (Settings → General → Keyboard); Siri language en-US with no download/progress indicator (Settings → Siri & Search → Language); an offline (Airplane Mode) dictation test into Notes worked. Asset presence confirmed; NOT full elimination (per ChatGPT review: Notes dictation ≠ this app's exact locale/request configuration).
2. **E5 — gain normalization A/B: DONE (2026-10-22), partial effect.** New loudnorm'd copies (`ffmpeg -af loudnorm=I=-16:TP=-1.5:LRA=11`, then explicitly resampled back to the originals' 48kHz/mono/pcm_f32le format — `loudnorm`'s true-peak limiting otherwise forces 192kHz output, which would have made sample rate a second variable) replayed via `replayChunked` on-device: mean level moved from -37.4/-38.1/-46.5 dB to roughly -17 to -19 dB. Fidelity: multi-a 9%→15% (43/288), multi-b 15%→43% (83/192, biggest jump), solo 19%→19% (28/149, unchanged). **Conclusion: level is a contributing factor but not sufficient alone — none cleared the 70% floor.**
3. **E6 — live-tap feed: DONE (2026-10-22), rules out a harness feed artifact.** New `FixtureReplayHarness.replayLiveTap` (real `AVAudioEngine`/`AVAudioPlayerNode`/`installTap`, not the manual `appendAudio` loop) reproduced the *same* tail-truncation pattern E3 found (e.g. multi-a: recognizer covered only offsets 50.0–53.2s of a 55s fed chunk, 9 words). **Conclusion: the manual feed loop is not the cause of tail-truncation** — a real engine tap shows it too. Caveats (per ChatGPT review): both paths still share request handling, result collection, and timing mapping (NOT ruled out — see E8), and the arms differed in session category (`.record` vs `.playAndRecord`) — see E10c. Artifact check: `endAudioBeforeFinal=true` in all E6 prints (harness calls endAudio, then awaits finals). (Fixed along the way: `replayLiveTap` needs `.playAndRecord`, not `.record`, for `AVAudioEngine.start()` to initialize an output unit at all — `.record` has no output route, which was failing with CoreAudio -10851. `replay`/`replayChunked` still use `.record` unchanged, matching production exactly.)
4. **E8 — raw callback/aggregation audit: DONE (2026-10-22). ROOT CAUSE FOUND.** `replay(frameRange:onCallback:)` logged every callback (partial+final) off raw `result.bestTranscription`, before any of our own mapping. Finding: within one continuous ~55s request, `segmentCount`/`transcriptLength` repeatedly **drop mid-stream** (segmentCount decreasing between consecutive callbacks). Hermes recount from the raw bundle log (`Test-Observatory-2026.10.22_19-59-35`, zstd-extracted): segmentCount drops in 30/318 callbacks (multi-a), 33/336 (multi-b), 21/345 (solo); counting any segmentCount-or-transcriptLength drop: 39/45/27 — identical pattern in all 3 trials per fixture. (Claude's original tallies of 43/424, 47/448, 31/460 are not reproducible from the bundle log under any counting definition — corrected 2026-10-22 by Hermes; the phenomenon and conclusion are unaffected.) **Conclusion drawn (scoped per ChatGPT review #2): on THIS device/OS/request configuration**, `SFSpeechRecognitionResult.bestTranscription` behaves with replacement-not-cumulative semantics across internal utterance boundaries — not established as a universal API rule. Caveats: small count-drops may be ordinary hypothesis revisions rather than utterance resets (only the large resets, e.g. 211→4 chars, are unambiguous); "every completed utterance appears intact in a pre-reset timestamped partial" is OBSERVED, not guaranteed; a similar disappear-after-pause behavior is anecdotally reported on Apple's developer forums (thread 762952) — corroboration, not a guarantee.
5. **E9 — short-passage control: DONE (2026-10-22). Confirms E8's mechanism.** A single clearly-audible 12s passage (`fixture-multi-b-loudnorm` 36–48s; `fixture-solo-loudnorm` 38–50s as secondary) recovers **fully** regardless of position when padded with silence (not competing speech): multi-b alone=28, start=29, end=37 words (vs. 28 in isolation); solo alone=20, start=20, end=18. Duration/position alone don't cause loss — loss only happens when *new speech* follows a pause (triggering E8's reset), confirmed by this negative control's clean recovery. Caveats (per ChatGPT review #2): "full recovery" is by word COUNT only, not alignment-verified — the same 12s passage yielding 28 (alone) vs 37 (end-position) is unexplained and could include insertions/repetitions; and the "new speech after a pause" trigger is inferred, not isolated (speech–pause–speech and continuous-speech controls with varied pause lengths were not run).
6. **E10 — controls & metric hygiene: DONE (2026-10-22).** (a) identity re-encode (no loudnorm) matches E3's baseline almost exactly (28/288, 29/192, 28/149 vs. E3's 27/288, 29/192, 28/149) — re-encoding itself is a non-factor. (b) per-fixture flat gain (peak-matched to -1.5dBFS, no dynamics compression: +12.0dB multi-a, +15.2dB multi-b, +18.7dB solo) recovers *most* of loudnorm's benefit for multi-a (28→37 vs. loudnorm's 43) and multi-b (29→76 vs. loudnorm's 83), but **solo stays flat at 28 regardless of gain method** — solo's floor is confirmed NOT level-related. (c) `.playAndRecord` re-run of the manual/chunked path matches `.record`'s E3 baseline almost exactly (27/288, 29/192, 28/149) — session category is not a confound in the E3-vs-E6 comparison. (d) 3x repeat trials throughout showed zero run-to-run variance when runs aren't contaminated by a preceding test's failure (see process note below). Metric caveats (now also in code comments): "fidelity" is a raw word-count ratio, not alignment-verified WER; `coveredOffsets` is a min–max range, not proof of continuous coverage.
7. **Process note:** an initial back-to-back run of all six E8–E10 tests produced near-zero words across nearly every E10 trial (contradicting E3's established baseline) immediately after two tests that threw uncaught errors (fixed: `replay`/`replayPassagePositionControl` now catch-and-continue on "No speech detected," matching `replayChunked`'s existing precedent). Re-running each test as a separate, isolated device action produced the clean numbers above — treat any future back-to-back multi-test device run's numbers with suspicion until corroborated by an isolated re-run.
8. **E7 — fixture re-record: still queued, lower priority.** Re-recording under the current `.measurement` capture config would not address E8's root cause (a recognition-session accumulation defect, not a capture-config or fixture-provenance issue) — still worth doing before a final Stage 0 verdict, but no longer the most informative next step.
- **New candidate fix (not yet scoped as a unit):** production could accumulate transcript content itself across each reset event (diff/concatenate on `segmentCount` drops) rather than trusting only the isFinal result's content — this is U2-adjacent and needs its own proposal/review before any code changes to `SpeechRecognitionManager.swift`.

  - **Orphaned header-only recording** (`5FF28F05….caf`, 4096 bytes, 22:16:22, duration unreadable): a recording started but never finalized — the crash/abandon path bypasses writer finalization (D-09's stop()-awaits-drain invariant holds only for clean stops).

- **Code-level hypothesis (unverified, not yet confirmed root cause):** grep across every Swift file in the app found zero handling of `scenePhase`/`UIApplication` background-foreground transitions anywhere — only `AVAudioSession.interruptionNotification` is observed (`SpeechRecognitionManager.swift:433`). `UIBackgroundModes: audio` is declared (Info.plist), so the app expects to keep running backgrounded, but nothing reacts to the transition itself.
