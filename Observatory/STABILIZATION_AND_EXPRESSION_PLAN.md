# Observatory: speech-pipeline stabilization + acoustic-expression observation (staged)

## Status
**Planned, not yet implemented**, as of 2026-10-15. This is the approved-pending-execution plan referenced from `ONBOARDING.md`. It went through two revisions after independent (ChatGPT) second-opinion review before reaching this state — see `ONBOARDING.md`'s "Process note" section for why that review step exists. Update the "Status" line and append an entry to `VERSION_HISTORY.txt` once any stage actually ships; don't let this drift into describing aspirational rather than real code (see `PROJECT_ARCHITECTURE.md`'s own stated policy on that).

## Context
This plan responds to an external review of `SpeechRecognitionManager.swift`, `SpeakerDiarizationEngine.swift`, and `ReflectionSessionStore.swift` against three real test recordings (saved transcripts + numeric audio measurements, not perceptual listening). Confirmed defects included: every saved word timestamp has `start == end` (callback-arrival time, not audio-derived); a data race between `endAudio()` and the realtime audio-append path; no stale-callback rejection across segment rollovers; a final-result-without-error case that silently stops recognition continuation; synchronous file I/O on the realtime audio thread with swallowed errors; diarization matching a whole transcript event against one wall-clock timestamp while RTTM segments are audio-file-relative; and a solo recording that got over-split into multiple "speakers."

Separately, the product's actual purpose was clarified: document and analyze **emotion through how speech is expressed** — prolonged sounds, compressed/accelerated delivery, possible reduced articulation, and changes in expression — where words are context, not the product. Stretching may *accompany* uncertainty; speeding up may *accompany* anger; neither *establishes* an emotion. Expressive-speech analysis is therefore a core workstream here, staged **after** stabilization (it depends on fixed timing/attribution), not deferred indefinitely.

**Non-negotiable framing for every stage below:** acoustic OBSERVATION (measured), tentative INTERPRETATION (bounded, revisable), and optional user SELF-REPORT/correction are three distinct, separately-persisted things. Nothing in this plan infers an actual felt emotion from deliberate test speech, and nothing asserts an emotion from a single acoustic cue.

## Stage 0 — Stabilize capture, timing, and attribution
- **Frame accounting must mean successful writes, not queue admission.** Track `capturedFrames` (tap thread, timestamped at capture), `enqueuedFrames`, and `writtenFrames` as three distinct counters. `framesWritten` (used for all downstream offset math) increments **only** on a confirmed successful `AVAudioFile.write` return, never on admission to the background writer's queue. Each buffer carries its own capture timestamp and generation tag from the tap thread outward — the background writer's admission/drain time is never used as a proxy for capture time.
- **No naive cumulative-frames ÷ current-rate division.** The recording format is fixed once per engine start (from `inputNode.outputFormat(forBus: 0)`); offset math uses that fixed rate for the span it actually applies to. If a format/rate change is ever detected mid-recording, it creates a new piecewise segment with its own rate for everything after the breakpoint — recording the breakpoint alone is not sufficient; the conversion math itself must branch on it.
- **Loss/overflow/write-failure propagates to both diarization and the new acoustic-expression features**, not diarization alone — both depend on the saved audio being complete and accurate. The writer's `audioRecordingReliable = false` + `missingAudioIntervals` gate both `SpeakerDiarizationEngine.label(session:)` and the Stage 1 acoustic-feature extraction below.
- **Flush before analysis**: `stop()`/`stopAndObserve()` await the writer's drain before the file is closed and before either diarization or acoustic-feature extraction opens it.
- Monotonic per-manager `requestGeneration` (never reset in `start()`); lock-unified `CurrentRequestBox.endAndClear()` closing the append/endAudio race; explicit per-generation lifecycle state (`active`/`finalizing`/`sealed`) with a single rollover decision per callback (handles Apple's final+error-in-one-callback case without double-sealing); bounded post-`endAudio` completion window; rapid-restart-loop guard.
- Optional (`nil`-means-unavailable, never `0`) `WordTiming.audioStart`/`audioEnd` with backward-compatible legacy decode; typed `DiarizationResult.segments` instead of RTTM parsing; word-level speaker matching; honest `Speaker.overlap`/`.unknown` instead of defaulting to `.user`; raw diarization audit data (segments + filtering decisions) persisted, not just counts.
- **Fixture handling**: the three saved test fixtures stay read-only baselines. `SpeakerDiarizationEngine.label(session:)` cannot recover timing the original pass discarded, so validation re-transcribes each saved `.caf` through the corrected recognition/timing path (a test-only replay harness feeding file buffers through the same code used live), then diarizes *that* output, writing comparisons to new files. The solo varied-delivery recording is now also the key fixture for Stage 1 acoustic-expression correctness, not just a diarization single-speaker check; the other two recordings exercise overlap/contamination handling for both diarization and expression-feature abstention.

## Stage 1 — Acoustic-expression OBSERVATION slice (first usable implementation)

### What's actually available on-device (inspected, not assumed)
- **`SFVoiceAnalytics`** (Speech framework, attached to `SFTranscriptionSegment`): per-frame `pitch`, `jitter`, `shimmer`, and `voicing` (0.0–1.0 voiced-probability), each an `SFAcousticFeature` with `frameDuration` + `acousticFeatureValuePerFrame`. This is Apple's own on-device acoustic analysis, already running inside the recognizer the app already uses — no new dependency, no external service. Exact enablement requirements get confirmed against the installed SDK at implementation time, not assumed from memory.
- **Locally derived from the now-fixed Stage 0 timing**: local speaking/articulation rate (words or syllable-estimate per second in a sliding window, not a single global words-per-minute), pause pattern and clustering (already measured acoustically by `SilenceTracker`, independent of ASR), and RMS-based relative intensity (already computed in `SilenceTracker`, extendable to a time-varying series instead of a single threshold check).
- **Pitch contour**: derived from `SFVoiceAnalytics.pitch` frames directly — no separate pitch-tracking implementation unless that API proves insufficient at implementation time, in which case the gap is reported, not silently worked around with an unvalidated DIY detector.

### Explicitly experimental or unsupported
- **Prolongation (stretched/dragged words)**: ASR word duration alone is not validated vowel-lengthening detection. First version flags a word as a *candidate* prolongation only when its duration is a statistical outlier relative to that **same speaker's own recent word durations within the session** (within-session baseline only — no cross-session baseline yet), with a crude phonetic-length normalizer (syllable-count estimate from the recognized text). Ships as a bounded, explicitly-labeled candidate signal with stated uncertainty, paired with the playable audio interval so a human can judge it directly.
- **Reduced articulation / slurring**: no defensible on-device detector is available (low ASR confidence and unusual pronunciation are explicitly not slurring). Ships as **unsupported** — the audio interval is preserved and surfaced for manual review, with a clear "not detected — no validated method available" status, rather than a misleading label.
- **Voice-quality features (jitter/shimmer)**: surfaced only where `SFVoiceAnalytics` actually reports them with usable frame coverage for a given segment; otherwise marked unavailable, not defaulted to a neutral value.

### Data model (reuses existing infrastructure — see `ObservationEvent` in `Models.swift`)
`ObservationEvent` (category `.voice`, already exists) already carries most of what's needed: `confidence: SignalQuality`, `engineVersion`, `relatedText`, `tags`, and — already present — `alternativeExplanations: [String]`, which is exactly the "allow mixed/unknown, no single forced reading" mechanism this needs. Additive, backward-compatible extensions, not a new model:
- `audioStart`/`audioEnd: TimeInterval?` — the playable source interval (same optional/nil-means-unavailable convention as `WordTiming`).
- `speaker: Speaker?` — reuses the Stage 0 `Speaker` enum (`.user`/`.other`/`.overlap`/`.unknown`), nil for event kinds that aren't speaker-attributed.
- A small `measurement: AcousticMeasurement?` struct (`value: Double`, `unit: String`, `method: String`) instead of burying units in prose `detail` text.
- New `ObservationEventKind` cases: `.prolongedSoundCandidate`, `.acceleratedDeliveryCandidate`, `.pitchContourShift`, `.intensityShift`, `.reducedArticulationUnsupported`.
- **Thresholds as data, not Swift constants** — per `PROJECT_CONSTRAINTS.md` #7 and the existing `SignalLibraryModels.swift`/`SignalDetectionRule` pattern already used for phrase-based signals: extend `SignalRuleMatchType` with an acoustic/numeric case (metric + comparison + threshold) rather than hardcoding the outlier ratio or rate-change threshold inline.
- **Per-speaker baseline, with explicit insufficient-coverage status**: computed only from a verified/selected speaker's own segments (excluding `.overlap`/`.unknown`/other-speaker audio), only once that speaker has adequate usable coverage. Below that minimum, baseline-dependent features report `insufficientBaseline` rather than silently using a tiny or cross-speaker sample. Within-session only in this stage.
- **Audio provenance recorded alongside every observation**: route/format/processing state active at capture time (category/mode, whether system Voice Isolation Mic Mode was active, sample rate) — because processing can alter the exact cues these features measure. No capture-side DSP change is made by assumption in this stage.

## Stage 2 — Bounded INTERPRETATION + user feedback (after Stage 1 ships observations)
- A separate tier of `ObservationEvent`s (or a thin extension reusing the same struct with `source: .derived`) referencing the originating Stage 1 observation by id (`derivedFromObservationID: UUID?`), offering a **tentative, explicitly non-exclusive** reading via `alternativeExplanations` — e.g. "possible uncertainty" alongside "possible emphasis" alongside "insufficient evidence," never a single asserted emotion. Any raw model/heuristic score is explicitly labeled "not a calibrated probability" unless a validation step establishes calibration — none exists yet, so none is claimed.
- **Self-report/correction**: a small `userCorrection: UserCorrection?` (`text: String`, `recordedAt: Date`) — matches `PROJECT_CONSTRAINTS.md` #5's existing "user confirmation or correction, when applicable" provenance field.
- **UI**: a minimal evidence-linked expression timeline added to `ReflectionDetailScreen.swift` (mirrored in `ObservatoryScreen.swift` per the existing diagnostics-duplication pattern) showing, per entry: the measured observation, the tentative meaning/alternatives, a playable excerpt, and an optional correction affordance. Only observations with an actual measurement behind them are shown.

## Delivery and acceptance
**First usable implementation, named concretely**: `SFVoiceAnalytics`-derived pitch/voicing/jitter/shimmer + Stage-0-timing-derived local rate/pause/intensity, surfaced as `ObservationEvent` entries per the schema above. On-device, no external service, no new package dependency. Prolongation is a labeled candidate signal; slurring is explicitly unsupported; nothing else is claimed.

**Testing strategy**:
- **Synthetic acoustic signals** (generated tones/sweeps/silence with known pitch, duration, amplitude) verify feature-extraction and timeline math correctness independent of real speech or recognition accuracy.
- **The three existing recordings**, via the Stage 0 replay harness, validate integration (features attach to the right audio interval, right speaker, right generation) — not perceptual/emotional accuracy.
- **Human annotation and self-report** are required for any claim about perceptual or emotional validity. Until that exists, every interpretation stays labeled tentative.
- **Concrete behavioral checks**: identical scripted text delivered at different speeds/stretching must be allowed to come back with no forced emotion label; injected noise/overlap/a simulated missing-audio-interval must trigger the insufficient-evidence/abstention path, not a confident label.

**Explicit limitations**: without reference annotations, no claim of emotion-recognition or slurring-detection accuracy is made anywhere in this work; no inference about actual felt emotional state is drawn from deliberate test speech or other speakers' words; numeric scores are not probabilities unless a separate calibration step says otherwise.

## Still explicitly out of scope
Perceptual ground-truth annotation at scale, further diarization-threshold retuning, full async `AVAudioSession` migration, SpeechAnalyzer/SpeechTranscriber A/B migration, and any external audio/ML service — no recording leaves the device without separate, explicit authorization.

## Verification
- `BuildProject` after each stage/major piece, not one large change.
- Swift Testing suite covering Stage 0 lifecycle/timing/diarization logic, plus Stage 1 synthetic-signal feature-math tests and replay-harness integration tests.
- Live smoke test for Stage 0 regressions (segment rollover past ~1 minute, an interruption).
- Final report on each stage distinguishes: what's measured and tested (structural/timing/feature-math correctness), what's integration-tested but not perceptually validated (real-recording replay), and what remains entirely unverified without human annotation (actual emotional/perceptual accuracy) — never collapsed into a single "works" claim.
